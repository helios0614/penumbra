# npm 供应链安全规范

本文定义 Penumbra 项目的依赖变更、日常核查、定期审计和应急响应要求。执行下列命令时，应进入包含 `package.json` 和 `package-lock.json` 的项目根目录；文档中的检查不能替代针对具体安全事件的 IOC 和日志分析。

## 1. 核心原则

- lockfile 是供应链安全的基础防线，但不是安全证明。它能固定解析结果、支持审查和复现，不能证明依赖代码没有恶意行为。
- `npm install` 可能执行第三方依赖的生命周期脚本，包括 `preinstall`、`install` 和 `postinstall`；不要在未确认变更内容和来源时直接运行。
- 下载量、版本号、签名和 provenance 只能提供流行度、标识或来源追踪信号，均不代表代码必然安全。
- `package-lock.json` 必须随依赖变更提交；CI 必须使用 `npm ci` 按 lockfile 安装。
- 禁止在没有明确、可审查理由的情况下删除 lockfile 后重新安装。确需重建时，应在 PR 中说明原因、工具版本和预期变化，并审查完整 diff。
- patch 和 minor 更新同样可能引入代码、脚本或依赖树变化，也需要检查，不得默认视为安全。

## 2. 检查分级与升级规则

默认先执行轻量检查。轻量检查发现无法解释的依赖来源、脚本、版本或 lockfile 变化时，立即升级为全面检查；一旦出现凭证滥用、异常访问或其他失陷迹象，跳过普通依赖问题处理，直接进入应急响应。

全面检查不是每次依赖操作的默认步骤。除异常升级外，每月或正式发布周期执行一次即可，并记录范围和结论。

## 3. 日常轻量检查

### 适用场景

- 新增或升级普通依赖。
- 审查依赖变更 PR。
- 收到安全通报后，先判断项目是否命中相关包、版本或传递依赖。
- 日常需要快速确认依赖状态。

### 执行步骤

在项目根目录执行：

```bash
git diff -- package.json package-lock.json
npm ls <包名> --all
npm audit --audit-level=high
```

其中 `<包名>` 替换为本次新增、升级或安全通报涉及的包名。若 `npm ls` 返回非零状态，应保留输出并判断是依赖树问题、peer dependency 问题，还是确实未安装该包；不要仅因退出码非零而忽略结果。

同时人工确认：

- lockfile 没有无原因的大面积重写。
- 没有新增陌生 Git URL、远程压缩包或来源异常的依赖。
- 没有异常的大版本跳升。
- 没有可疑、拼写相近或疑似 typosquatting 的包名。
- 根项目和新增依赖没有突然增加 `preinstall`、`install`、`postinstall`。
- CI 仍然使用 `npm ci`。

轻量检查只能发现明显异常，不代表完成了完整的恶意代码排查。`npm audit` 的无告警结果也仅表示在其当前 advisory 覆盖范围内未报告匹配项。

## 4. 全面检查

### 触发条件

出现任一条件即升级：

- 命中已知恶意包或恶意版本。
- 出现未知或无法解释的生命周期脚本。
- lockfile 出现无法解释的大面积变化。
- npm、GitHub、云平台、Kubernetes 等出现异常访问或凭证使用。
- 仓库中出现未知工作流、IDE 或 AI 编程工具配置。
- 到达每月或正式发布周期的定期审计节点。

### 执行步骤

在隔离或可丢弃的干净工作副本中，使用仓库提交的 lockfile 安装但不执行生命周期脚本：

```bash
npm ci --ignore-scripts
npm audit
npm audit signatures
```

随后完成以下检查并保存命令输出、文件 diff、时间范围和结论：

- 检查所有直接和传递依赖的生命周期脚本，确认脚本内容、引入版本和执行目的；对未知脚本保持不执行状态，直到完成审查。
- 根据安全通报搜索对应 IOC，包括包名与版本、文件名、域名、URL、IP、哈希、命令片段和异常环境变量访问。
- 检查 `package.json`、`package-lock.json` 和 `.npmrc` 的依赖来源、registry、认证、脚本及配置变化。
- 检查 `.github/workflows/**` 中未知 action、外部脚本下载、权限扩大、secret 使用和持久化步骤。
- 检查 `.vscode/tasks.json` 和 `.claude/settings.json` 中自动执行的命令、hooks、权限与未知配置。
- 检查 npm 发包、GitHub 提交与 workflow、CI Runner，以及云平台访问日志；将日志时间线与依赖变更、安装和构建时间对齐。
- 出现失陷迹象时立即进入应急响应，不再作为普通依赖问题继续处理。

## 5. 应急响应

按以下顺序执行：

1. 停止继续运行项目或安装依赖。
2. 隔离开发机或 CI Runner，避免继续访问生产和内部网络。
3. 保存日志和现场证据，包括时间线、进程、网络连接、构建产物和相关文件；不要先清理现场。
4. 从可信设备撤销并轮换 npm、GitHub、云平台、Kubernetes、Vault、SSH 等凭证。
5. 审计异常发包、提交、工作流和云端访问，确认受影响的账号、仓库、Runner、环境与时间范围。
6. 检查 `.vscode`、`.claude` 和 CI 持久化配置，移除前先记录证据和来源。
7. 从可信环境重新构建；删除 `node_modules` 只会移除局部文件，不应视为完整恢复。
