# Penumbra 本地构建与独立部署指南（Codex）

## 1. 项目说明

Penumbra 是一个独立前端项目，使用 Vue/React 以外的 React 技术栈（实际以 package.json 为准），通过 Vite 构建静态资源。

项目支持独立构建，最终产物为 `dist/`。

当前项目已经具备：

- GitHub Actions 自动构建与测试（`.github/workflows/build.yml`）。
- 手动发布静态产物（`.github/workflows/deploy.yml`）。
- 发布产物完整性校验。
- Python 静态产物安装器（`scripts/deploy/install.py`）。
- 安装、版本记录、回滚及异常恢复机制。

正式操作前，优先阅读：

- `docs/deploy-artifacts.md`
- `docs/ubuntu-deployment.md`

## 2. 本地构建

基本流程：

```
npm ci
npm test
npm run build
```

构建前先检查 Node.js 版本及项目依赖要求。

构建完成后检查：

- `dist/index.html`
- JS、CSS 等静态资源。
- 图片、字体等资源。
- 资源引用是否完整。
- 构建是否正确使用预期的 Base Path。

不要直接假定本地构建成功就代表可以部署。

## 3. 两种构建方式

### 方式 A：本地构建

适合个人开发和测试。

从 Git 仓库拉取代码，在本地安装依赖、运行测试、构建，再根据自己的服务器环境部署 `dist/`。

不要求必须配置 GitHub Actions。

### 方式 B：GitHub Actions

适合稳定、可追溯的正式发布。

当前项目流程：

1. Push 到 main，自动执行测试和构建。
2. 手动触发 Publish deploy artifact。
3. 指定完整源码 Commit SHA。
4. 构建并校验生产产物。
5. 发布到 deploy 分支，生成独立 Artifact Commit。
6. 使用固定 Artifact SHA 获取指定版本。

不要使用 latest、分支 HEAD 等可变标识代替正式发布版本。

如果使用 Fork 或自己的 GitHub 仓库，需要先检查 Workflow 权限、仓库地址、发布器及安装器的仓库身份约束，不能假定复制文件后就能直接运行。

## 4. 独立部署注意事项

部署前必须先了解自己的后端环境。

Penumbra 不只是静态页面，还需要对应后端提供：

- 登录认证。
- `/api/*` API。
- `/ws` WebSocket。
- Penumbra 静态页面路由。
- SPA 深链接回退。

前端默认使用同源 API 和 WebSocket 路径，因此部署时需要确认前后端域名、路径及认证方式一致。

当前项目使用 `/penumbra/` 作为 Base Path。若部署到其他路径，必须重新检查并构建，不能仅修改服务器目录名称。

## 5. 服务器部署原则

部署前让 Codex 先检查：

- 操作系统与 Python 版本。
- 现有后端服务及静态路由。
- 域名和反向代理配置。
- 部署目录及权限。
- 服务器 GitHub 访问能力。
- 磁盘空间。
- 现有静态文件及历史部署状态。

不要未经检查直接覆盖已有网站。

正式部署应遵循：

1. 固定完整 Artifact SHA。
2. 获取并校验发布元数据及全部文件哈希。
3. 在独立暂存目录准备资源。
4. 先安装静态资源。
5. 最后原子替换 `index.html`。
6. 保留旧版本及旧哈希资源。
7. 验证成功后再考虑后续升级。

禁止直接在生产服务目录执行 `git pull` 来更新前端。

## 6. 特别注意

- 不要把其他人的服务器地址、SSH 私钥、Token、Cookie 或 `.env` 复制到项目中。
- 不要将生产凭据写入 Git 或提交到 GitHub。
- SSH 使用独立密钥，尽量遵循最小权限原则。
- 不要未经确认修改 systemd、Nginx、Cloudflare Tunnel 等现有服务。
- 不要为了部署前端重启不相关的后端服务。
- 不要随意删除旧静态资源，避免旧页面仍引用的 JS/CSS 失效。
- 不要将其他人的部署路径、域名和目录权限当作通用配置。
- 部署失败时先停止并保留现场，不要自动清理生产目录。

## 7. 给 Codex 的工作要求

请先阅读项目现有部署文档和脚本，再结合当前服务器环境制定部署方案。

遵循以下原则：

1. 优先复用项目已有构建、发布和校验工具。
2. 不要重复实现已经存在的功能。
3. 不要未经审计修改后端业务代码。
4. 先只读检查，再提出实施方案。
5. 涉及生产文件修改、服务重启、部署和回滚时，先说明影响并获得用户确认。
6. 每个阶段报告实际执行结果，不要将计划执行描述为已完成。

最终目标：让 Penumbra 能够在独立环境中完成本地构建、产物校验和安全部署，同时不破坏原有后端及其他前端服务。
